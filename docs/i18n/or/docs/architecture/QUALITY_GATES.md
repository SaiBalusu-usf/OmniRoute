ଏହି ଡକ୍ୟୁମେଣ୍ଟଟି OmniRoute ର ସମସ୍ତ CI ଗୁଣବତ୍ତା ଗେଟ୍ ପାଇଁ ପ୍ରାମାଣିକ ସନ୍ଦର୍ଭ।
ଏହା ପ୍ରତ୍ୟେକ ଗେଟ୍, ଏହା କ’ଣ ଯାଞ୍ଚ କରେ, କେଉଁ CI ଜବ୍ରେ ଏହା ଚାଲେ, ଏହା
ଏକ ରାଚେଟ୍ ବେସ୍ଲାଇନ୍ କିମ୍ବା ଏକ ପାସ୍/ଫେଲ୍ ନୀତି ବ୍ୟବହାର କରେ କି ନାହିଁ, ଏବଂ ଏହା ବିଲ୍ଡ୍କୁ ଅବରୋଧ କରେ କିମ୍ବା କେବଳ ପରାମର୍ଶମୂଳକ—ତାହା ବର୍ଣ୍ଣନା କରେ।

ଏକ ସଂକ୍ଷିପ୍ତ ସାରାଂଶ ଏବଂ ଅନୁମତି-ତାଲିକା ନୀତି ପାଇଁ, `AGENTS.md` ରେ ଥିବା
"ଗୁଣବତ୍ତା ଗେଟ୍ ଏବଂ ରାଚେଟ୍" ବିଭାଗ ଦେଖନ୍ତୁ। ସେହି ସିଷ୍ଟମ୍ର ସମାଲୋଚନାମୂଳକ ମୂଲ୍ୟାଙ୍କନ,
ପରିପକ୍ୱତା ବର୍ଗୀକରଣ ଏବଂ ଟୁଲ୍-ନିରପେକ୍ଷ ପ୍ରତିରୂପଣ ଯୋଜନା ପାଇଁ,
[ଗୁଣବତ୍ତା ଗେଟ୍ ପ୍ଲେବୁକ୍](../ops/QUALITY_GATE_PLAYBOOK.md) ଦେଖନ୍ତୁ।

## ଗେଟ୍ ତାଲିକା (~90 ସ୍କ୍ରିପ୍ଟ)

ସ୍କ୍ରିପ୍ଟଗୁଡ଼ିକ `scripts/check/` (ନୀତି ଗେଟ୍) ଏବଂ `scripts/quality/` (ରାଚେଟ୍ ଇଞ୍ଜିନ୍) ଅଧୀନରେ ରହିଛି।
CI ର ନିର୍ଭରଯୋଗ୍ୟ ମୂଳ ଉତ୍ସ ହେଉଛି `.github/workflows/ci.yml`।

### ରିଲିଜ୍ PR ଫାଷ୍ଟ-ପାଥ୍ (`quality.yml`)

#### ଭୁଲିଯାଇଥିବା ସହୋଦର ପରୀକ୍ଷା ରିପୋର୍ଟ

`npm run check:forgotten-sibling-tests` ପରୀକ୍ଷା-ପ୍ରଭାବ ମ୍ୟାପ୍ ପଛରେ ଥିବା ଇମ୍ପୋର୍ଟ ରିଜଲ୍ଭର୍କୁ ପୁନଃବ୍ୟବହାର କରେ।
ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତିତ ପ୍ରଡକ୍ସନ୍ ମଡ୍ୟୁଲ୍ ପାଇଁ, ସମ୍ଭାବ୍ୟ ପରୀକ୍ଷାଟି
pull-request ଡିଫ୍ରେ ନଥିଲେ, ଏହା ନିର୍ଦ୍ଧାରିତ
`ପରିବର୍ତ୍ତିତ ମଡ୍ୟୁଲ୍/ସଙ୍କେତ -> ସ୍ଥିର ବ୍ୟବହାରକାରୀ -> ସମ୍ଭାବ୍ୟ ସହୋଦର ପରୀକ୍ଷା` ଶୃଙ୍ଖଳ ରିପୋର୍ଟ କରେ। କୌଣସି ଅବରୋଧକ ରୋଲ୍ଆଉଟ୍ ପୂର୍ବରୁ କ୍ୟାଲିବ୍ରେସନ୍ ପାଇଁ
Markdown ସାରାଂଶ ଏବଂ JSON ଫଳାଫଳକୁ `forgotten-sibling-tests` ୱାର୍କଫ୍ଲୋ ଆର୍ଟିଫ୍ୟାକ୍ଟ ଭାବେ ସଂରକ୍ଷିତ ରଖାଯାଏ।

ବ୍ୟାରେଲ୍ ରି-ଏକ୍ସପୋର୍ଟ୍ ଏବଂ ଡାଇନାମିକ୍ ଇମ୍ପୋର୍ଟଗୁଡ଼ିକ କେବଳ ରିଜୋଲ୍ୟୁସନ୍ ନିଦାନ; ସେଗୁଡ଼ିକ କେବେ ମଧ୍ୟ
ଅବରୋଧକ ଫାଇଣ୍ଡିଂ ସୃଷ୍ଟି କରନ୍ତି ନାହିଁ। ସମୀକ୍ଷା କରାଯାଇଥିବା ବ୍ୟତିକ୍ରମଗୁଡ଼ିକ
`config/quality/forgotten-sibling-allowlist.json` ରେ ରହିଛି। ପ୍ରତ୍ୟେକ ଏଣ୍ଟ୍ରିରେ ବ୍ୟବହାରକାରୀ ଏବଂ ସମ୍ଭାବ୍ୟ
ପରୀକ୍ଷାର ନାମ, ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ ଯୁକ୍ତି, ଏବଂ ଏକ GitHub issue କିମ୍ବା pull request ର ଲିଙ୍କ୍ ରହିବା ଆବଶ୍ୟକ। ତ୍ରୁଟିପୂର୍ଣ୍ଣ ଏଣ୍ଟ୍ରିଗୁଡ଼ିକ
ବନ୍ଦ ଅବସ୍ଥାରେ ବିଫଳ ହୁଏ। ବ୍ୟତିକ୍ରମଗୁଡ଼ିକ ଡିଲିଟ୍ ହୋଇଥିବା ସମ୍ଭାବ୍ୟ ପରୀକ୍ଷା କିମ୍ବା `.skip`/`.todo` ଯୋଡ଼ୁଥିବା ଡିଫ୍କୁ ଦମନ କରିପାରିବ ନାହିଁ;
ଆସର୍ସନ୍ ଦୁର୍ବଳୀକରଣ ଏବଂ ଅନ୍ୟାନ୍ୟ ମାସ୍କିଂ ସ୍ୱାଧୀନ ଭାବେ ଅବରୋଧକ
`check:test-masking` ଗେଟ୍ର ଅଧୀନରେ ରହେ।

- `check-ui-keys-coverage` କୀର _ଉପସ୍ଥିତି_ ଗଣନା କରେ, ତେଣୁ ଏକ ପୁରୁଣା ଅନୁବାଦ କଭର୍ ହୋଇଥିବା ଭାବେ ଗଣାଯାଏ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` ଡକ୍ୟୁମେଣ୍ଟେସନ୍ ମିରର୍ଗୁଡ଼ିକୁ ଟ୍ରାକ୍ କରେ —
  ଏହା କେବେବି `src/i18n/messages/*.json` ପଢ଼େ ନାହିଁ। 2026-09 ପୁନଃ-ସିଙ୍କ୍ ପରଠାରୁ ଜବ୍ `docs-sync-strict`-ରେ ଅବରୋଧକ: ଏକ ମୂଳ ଡକ୍ୟୁମେଣ୍ଟ ସମ୍ପାଦନା କରନ୍ତୁ → `npm run i18n:run -- --files=<doc>` (ବିଭାଗ-ସ୍ତରୀୟ, କମ୍ ଖର୍ଚ୍ଚସାଧ୍ୟ)।

**ପାର୍ଥକ୍ୟ-ସଚେତନ, ବେସ୍ଲାଇନ୍-ସମର୍ଥିତ ନୁହେଁ।** ଏହା ମର୍ଜ୍ ବେସ୍ରେ ଥିବା `en.json` ସହିତ
କାର୍ଯ୍ୟରତ ଟ୍ରିକୁ ତୁଳନା କରେ; ଯେଉଁ ପ୍ରତ୍ୟେକ କୀର ଇଂରାଜୀ ମୂଲ୍ୟ ପରିବର୍ତ୍ତିତ ହୋଇଛି, ସେଥିପାଇଁ ଅପରିବର୍ତ୍ତିତ
ଅନୁବାଦ ଧାରଣ କରିଥିବା ଯେକୌଣସି ଲୋକେଲ୍ ପୁରୁଣା। ଏହା ଜାଣିଶୁଣି **ପୂର୍ବରୁ ଥିବା ବକେୟାକୁ ସ୍ଥିର କରେ** — ଦୀର୍ଘଦିନ ଧରି ଥିବା ଅନୁବାଦ କେଉଁ ପୁରୁଣା ଇଂରାଜୀରୁ ଆସିଥିଲା ତାହା ଏକ ପାର୍ଥକ୍ୟ
ପ୍ରକାଶ କରିପାରେ ନାହିଁ, ତେଣୁ ଗେଟ୍ କେବଳ ବର୍ତ୍ତମାନର ପରିବର୍ତ୍ତନ ଯାହାକୁ ସ୍ପର୍ଶ କରେ ତାହାକୁ ବିଚାର କରେ। ବିକଳ୍ପଟି (ପ୍ରତି-କୀ ହ୍ୟାସ୍ ବେସ୍ଲାଇନ୍) ପାଇଁ
ପ୍ରାୟ 600 KB ଉତ୍ପାଦିତ ଫାଇଲ୍ ଆବଶ୍ୟକ ହେବ, ଯାହା ସବୁଠାରୁ ବଡ଼ ବିଦ୍ୟମାନ ବେସ୍ଲାଇନ୍ର 3× ଏବଂ ପ୍ରତ୍ୟେକ i18n PR-ରେ ପରିବର୍ତ୍ତିତ ହେବ।

ଏହାକୁ ସନ୍ତୁଷ୍ଟ କରିବାର ଦୁଇଟି ଉପାୟ:

1. ପ୍ରଭାବିତ ଅନୁବାଦଗୁଡ଼ିକୁ ଅଦ୍ୟତନ କରନ୍ତୁ, କିମ୍ବା
2. ସେଗୁଡ଼ିକୁ `__MISSING__:<new english>` ଭାବେ ସେଟ୍ କରନ୍ତୁ — ତା’ପରେ ରନ୍ଟାଇମ୍ ସଂଶୋଧିତ ଇଂରାଜୀ ପରିବେଷଣ କରେ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ଏବଂ କୀଟି ଅନୁବାଦ ପାଇଁ ଧାଡ଼ିରେ ଯୋଡ଼ାଯାଏ।

ଯଦି ଷ୍ଟ୍ରିଙ୍ଗ୍ର **ଅର୍ଥ** ପରିବର୍ତ୍ତିତ ହୋଇଛି, ତେବେ **କୀର ନାମ ପରିବର୍ତ୍ତନ** କରିବାକୁ ପ୍ରାଧାନ୍ୟ ଦିଅନ୍ତୁ: ଏକ ନୂଆ କୀ
ପୁରୁଣା ଅନୁବାଦ ଉତ୍ତରାଧିକାରରେ ପାଇପାରିବ ନାହିଁ। #8463 ଏହି ପ୍ୟାଟର୍ନ ବ୍ୟବହାର କରିଥିଲା।

```bash
npm run i18n:check-value-drift          # କଠୋର (CI ଯାହା ଚଲାଏ)
npm run i18n:check-value-drift:warn     # କେବଳ ରିପୋର୍ଟ
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ବେସ୍ କ୍ୟାଟାଲଗ୍ ପଢ଼ାଯାଇପାରିବ ନାହିଁ (ବେସ୍ ref ବିନା ଶ୍ୟାଲୋ
କ୍ଲୋନ୍) ବେଳେ `check-openapi-breaking`-କୁ ଅନୁସରଣ କରି, `SKIP reason=base-unresolved` ସହିତ 0 ଏକ୍ଜିଟ୍ କରେ।

## ଅନୁମୋଦିତ-ତାଲିକା ନୀତି

ପୂର୍ବରୁ ଥିବା ଉଲ୍ଲଂଘନ ଯୋଗୁଁ ବିଫଳ ହୋଇପାରୁ ନଥିବା ପ୍ରତ୍ୟେକ ଗେଟ୍ ଏକ ଅପରିବର୍ତ୍ତନୀୟ ଅନୁମୋଦିତ-ତାଲିକା ବ୍ୟବହାର କରେ
(ଯଥା, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)। ନୀତିଟି ହେଉଛି:

**ମୂଳ କାରଣଟି ସମାଧାନ କରନ୍ତୁ; ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲେ ଏବଂ ସେହି PRରେ
ସମାଧାନ କରାଯାଇପାରୁ ନଥିଲେ ମାତ୍ର ଅନୁମୋଦିତ-ତାଲିକା ବ୍ୟବହାର କରନ୍ତୁ।**

ଏକ ଅନୁମୋଦିତ-ତାଲିକାରେ ଏଣ୍ଟ୍ରି ଯୋଡ଼ିବାବେଳେ:

1. ଯଥାର୍ଥତାର କାରଣ ସହିତ ଏକ ମନ୍ତବ୍ୟ ଅନ୍ତର୍ଭୁକ୍ତ କରନ୍ତୁ।
2. ଟ୍ରାକିଂ ଇସ୍ୟୁକୁ ଉଲ୍ଲେଖ କରନ୍ତୁ (ଯଥା, `// #3498 — ପର୍ଯ୍ୟାୟ 2 ବୈଶିଷ୍ଟ୍ୟ, ଏପର୍ଯ୍ୟନ୍ତ କାର୍ଯ୍ୟକାରୀ କରାଯାଇନାହିଁ`)।
3. ଉଲ୍ଲଂଘନଟି ସମାଧାନ କରୁଥିବା ସେହି PRରେ ଏଣ୍ଟ୍ରିଟି ହଟାନ୍ତୁ — ଆଉ କୌଣସି ସକ୍ରିୟ ଉଲ୍ଲଂଘନକୁ
   ଦମନ କରୁ ନଥିବା ଏକ ଅଚଳ ଏଣ୍ଟ୍ରି ନିଜେ ଏକ ତ୍ରୁଟି (କାର୍ଯ୍ୟକାରୀ ହେବା ପରେ 6A.3 ଅଚଳ-ପ୍ରବର୍ତ୍ତନ
   ଏକ ଅନାଥ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି ପାଇଁ ଗେଟ୍କୁ ବିଫଳ କରିବ)।

ପରୀକ୍ଷାଗୁଡ଼ିକୁ ଶୀଘ୍ର ପାସ୍ କରାଇବା ପାଇଁ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି ଯୋଡ଼ନ୍ତୁ **ନାହିଁ**। ବଢ଼ୁଥିବା
ଅନୁମୋଦିତ-ତାଲିକା ସହିତ ଏକ ସବୁଜ ଗେଟ୍ ଗୁଣବତ୍ତାର ଏକ ମିଥ୍ୟା ଆଶ୍ୱାସନ।

### ଆପଣଙ୍କ PRରେ ଏକ ଗେଟ୍ ବିଫଳ ହେଲେ

1. **ଗେଟ୍ର ଆଉଟପୁଟ୍ ଯତ୍ନର ସହ ପଢ଼ନ୍ତୁ** — କେଉଁ ଫାଇଲ୍ କିମ୍ବା ସିମ୍ବଲ୍ ନିୟମଟି ଉଲ୍ଲଂଘନ କରିଛି, ଏହା ଆପଣଙ୍କୁ ଠିକ୍ ଭାବରେ କହିଥାଏ।
2. **ଉଲ୍ଲଂଘନଟି ସମାଧାନ କରନ୍ତୁ** — ଅଧିକାଂଶ ଗେଟ୍ ନିର୍ଦ୍ଧାରଣାତ୍ମକ ଫାଇଲ୍ସିଷ୍ଟମ୍ ଯାଞ୍ଚ, ଯାହା କୋଡ୍
   ସଠିକ୍ ହେବାମାତ୍ରେ ପାସ୍ ହୋଇଯାଏ।
3. **ଯଦି ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲା** (ଅର୍ଥାତ୍, ଆପଣ ଏହାକୁ ସୃଷ୍ଟି କରିନାହାନ୍ତି, କିନ୍ତୁ ଗେଟ୍ ବର୍ତ୍ତମାନ
   ଏହାକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରୁଛି): ଯଥାର୍ଥତାର ମନ୍ତବ୍ୟ ଏବଂ ଏକ ଟ୍ରାକିଂ ଇସ୍ୟୁ ସହିତ ଏକ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି ଯୋଡ଼ନ୍ତୁ।
4. **ଯଦି ଗେଟ୍ଟି ଏକ ରାଚେଟ୍ ଅଟେ** (କଭରେଜ୍, ESLint ଚେତାବନୀ, ପୁନରାବୃତ୍ତି, ଜଟିଳତା):
   ଆପଣଙ୍କ ପରିବର୍ତ୍ତନ ମେଟ୍ରିକ୍କୁ ଆହୁରି ଖରାପ କରିଛି। ଅନ୍ତର୍ନିହିତ ସମସ୍ୟାଟି ସମାଧାନ କରନ୍ତୁ, କିମ୍ବା (କ୍ୱଚିତ୍) ପରିବର୍ତ୍ତନଟି ଉଦ୍ଦେଶ୍ୟମୂଳକ ଏବଂ ମେଟ୍ରିକ୍ର
   ଅବନତି ଗ୍ରହଣଯୋଗ୍ୟ ହେଲେ `npm run quality:ratchet -- --update` ଚଲାନ୍ତୁ — କିନ୍ତୁ PR ବିବରଣୀରେ ଏହାର କାରଣ ଲିପିବଦ୍ଧ କରନ୍ତୁ।
5. **ପରାମର୍ଶମୂଳକ ଗେଟ୍ଗୁଡ଼ିକ** (`continue-on-error: true`) କେବଳ ସୂଚନାମୂଳକ — ସେଗୁଡ଼ିକ ମର୍ଜ୍କୁ ଅବରୋଧ
   କରେନାହିଁ, କିନ୍ତୁ CI ସାରାଂଶରେ ଦେଖାଯାଏ। ତଥାପି ସେଗୁଡ଼ିକୁ ସମାଧାନ କରନ୍ତୁ।

### ମର୍ଜ୍ / ଡିଡୁପ୍ଲିକେସନ୍ (ଯାନ୍ତ୍ରିକ, କମ୍ ବିପଦ)

ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀକୁ 2026-06-17 ର ଲାଇଭ୍ ଗେଟ୍ ସ୍ଥିତି ସହିତ ଯାଞ୍ଚ କରାଯାଇଥିଲା (ବିଶ୍ୱାସ କରନ୍ତୁ, କିନ୍ତୁ ଯାଞ୍ଚ ମଧ୍ୟ କରନ୍ତୁ);
ଅନେକ "ସ୍ପଷ୍ଟ" ମର୍ଜ୍ ପ୍ରକୃତରେ ଲୁକ୍କାୟିତ ଋଣ ଲୁଚାଇଥିବା ଜଣାପଡ଼ିଲା ଏବଂ ସେଗୁଡ଼ିକ **ସିଧାସଳଖ ପ୍ରତିସ୍ଥାପନଯୋଗ୍ୟ ନୁହେଁ**।

- **`check:docs-sync` ଦୁଇଥର ଚାଲେ** — `lint` ଜବ୍ରେ ସ୍ୱତନ୍ତ୍ର ଭାବରେ ଏବଂ ପୁନର୍ବାର `check:docs-all` (`docs-sync-strict`) ଓ husky pre-commit hook ଭିତରେ। ✅ **ସମ୍ପୂର୍ଣ୍ଣ** — ସ୍ୱତନ୍ତ୍ର `lint` ଆହ୍ୱାନ ଅପସାରିତ।
- **CVE ସ୍କାନିଂ** — ❌ **ଏହା ଏକ ସହଜ ମର୍ଜ୍ ନୁହେଁ।** `audit:deps` ଯେକୌଣସି high/critical CVE ରେ ହାର୍ଡ-ଫେଲ୍ କରେ; `check:vuln-ratchet` (osv) କେବଳ ବେସଲାଇନ୍ ତୁଳନାରେ ଏକ _ରିଗ୍ରେସନ୍_ ହେଲେ ବିଫଳ ହୁଏ (ବର୍ତ୍ତମାନ 1 MODERATE)। ଅର୍ଥବିଧି ଭିନ୍ନ — `audit:deps` ବାଦ ଦେଲେ ପରମ high/critical ଗେଟ୍ ହରାଇଯିବ। ଉଭୟକୁ ରଖନ୍ତୁ।
- **ସାଇକଲ୍ ଚିହ୍ନଟ** — ❌ **ଏହା ଏକ ସହଜ ମର୍ଜ୍ ନୁହେଁ।** `check:circular-deps` (dpdm) **91ଟି ସାଇକଲ୍** ରିପୋର୍ଟ କରେ (ସେଥିପାଇଁ ଏହା ପରାମର୍ଶମୂଳକ); ପ୍ରଥମେ ସେଗୁଡ଼ିକର ସମାଧାନ ନକରି ଏହାକୁ ବ୍ଲକିଂକୁ ଉନ୍ନୀତ କରାଯାଇପାରିବ ନାହିଁ, ଏବଂ ସବୁଜ, ସୁପରିଚାଳିତ `check:cycles` ତୁଳନାରେ ଏହାର ପରିସର ଅଧିକ ବ୍ୟାପକ। `check:cycles` କୁ ବ୍ଲକିଂ ଭାବେ ରଖନ୍ତୁ; 91ଟି dpdm ସାଇକଲ୍ର ସମାଧାନ ଏକ ପୃଥକ ବ୍ୟାକଲଗ୍।
- **ଜଟିଳତା** — ✅ **ସମ୍ପୂର୍ଣ୍ଣ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ଗୋଟିଏ ESLint ୱାକ୍, ruleId ଅନୁସାରେ ଗଣନା କରେ ଯାହାଦ୍ୱାରା cyclomatic+max-lines ଏବଂ cognitive ବେସଲାଇନ୍ଗୁଡ଼ିକ ସ୍ୱାଧୀନ ରହେ; ବ୍ୟକ୍ତିଗତ `check:complexity` / `check:cognitive-complexity` ସ୍ଥାନୀୟ `--update` ପାଇଁ ରହିଛି।
- **`/api` ଆଣ୍ଟି-ହାଲୁସିନେସନ୍** — ✅ **ସମ୍ପୂର୍ଣ୍ଣ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api` ର ଗୋଟିଏ FS ଇନଭେଣ୍ଟରି, openapi-routes + docs-symbols ଏବେ ମଧ୍ୟ ସ୍ୱାଧୀନ ଭାବେ ରିପୋର୍ଟ କରେ; ବ୍ୟକ୍ତିଗତଗୁଡ଼ିକ ସ୍ଥାନୀୟ ରନ୍ ପାଇଁ ରହିଛି।
- **`check:node-runtime` 11ଟି ଜବ୍ରେ ଚାଲେ** — ⚠️ **କମ୍ ROI।** ପ୍ରତ୍ୟେକଟି ଏକ ପୃଥକ ରନର୍ ଏବଂ ଯାଞ୍ଚଟି <1s; ମୋଟ ସଞ୍ଚୟ ~10s, କିନ୍ତୁ ଏହା ବଦଳରେ ଏକ ସସ୍ତା ପ୍ରତି-ଜବ୍ ସୁରକ୍ଷା ହରାଇବ। ପରିବର୍ତ୍ତନଜନିତ ଅସ୍ଥିରତା ପାଇଁ ଏହା ଯୋଗ୍ୟ ନୁହେଁ।
- **CI lint ରେ `typecheck:noimplicit:core`** — ✅ **lint ଜବ୍ରୁ ଅପସାରିତ** (ଏହା ପରାମର୍ଶମୂଳକ `continue-on-error` ଥିଲା); ବ୍ଲକିଂ ଟାଇପ୍ ସର୍ଫେସ୍ ହେଉଛି `typecheck:core` + `check:type-coverage`। ସ୍ଥାନୀୟ ସ୍କ୍ରିପ୍ଟ ରଖାଯାଇଛି।

### ଫ୍ଲିପ୍ / ନିଷ୍ପତ୍ତି (ଅପରେଟର ନୀତି)

- `check:openapi-security-tiers` (ପରାମର୍ଶମୂଳକ) — ❌ **ସହଜରେ ଫ୍ଲିପ୍ କରାଯାଇପାରିବ ନାହିଁ।** ଏହା 0 ସହିତ ପ୍ରସ୍ଥାନ କରେ, କିନ୍ତୁ ସତର୍କ କରେ ଯେ `LOCAL_ONLY_API_PREFIXES` ଅଧୀନରେ ଥିବା ଅନେକ `traffic-inspector` ରୁଟ୍ରେ `x-loopback-only: true` ଟିପ୍ପଣୀ ନାହିଁ। ଏହାକୁ ବାଧ୍ୟତାମୂଳକ କରିବା ପାଇଁ ପ୍ରଥମେ `openapi.yaml` ରେ ସେହି ଟିପ୍ପଣୀଗୁଡ଼ିକ ଯୋଡ଼ିବା ଆବଶ୍ୟକ।
- `typecheck:noimplicit:core` (ପରାମର୍ଶମୂଳକ) — ବ୍ଲକିଂ `check:type-coverage` ରାଚେଟ୍ ଦ୍ୱାରା ମୁଖ୍ୟତଃ ଅନ୍ତର୍ଭୁକ୍ତ। ଏହାକୁ ଏକ ରାଚେଟ୍କୁ ଫ୍ଲିପ୍ କରନ୍ତୁ କିମ୍ବା ଅନାବଶ୍ୟକ ଦ୍ୱିତୀୟ `tsc` ପାସ୍କୁ ବାଦ ଦିଅନ୍ତୁ।
- `test:vitest:ui` (ବର୍ତ୍ତମାନ **ବ୍ଲକିଂ**) — ପୂର୍ବରୁ ଥିବା ବିଫଳତାଗୁଡ଼ିକୁ `vitest.config.ts` ରେ `// #8618` ଟ୍ରାକିଂ ମନ୍ତବ୍ୟ ସହିତ ସ୍ପଷ୍ଟ ଭାବେ ବାଦ ଦିଆଯାଇଛି; ନୂତନ ବିଫଳତା ଜବ୍କୁ ବିଫଳ କରେ।
- `check:secrets` (gitleaks, 3ଟି ଦସ୍ତାବିଜଭୁକ୍ତ ମିଥ୍ୟା-ପଜିଟିଭ୍ରେ ଫ୍ରିଜ୍ ହୋଇଥିବା ବ୍ଲକିଂ ରାଚେଟ୍) — 0 ରେ ପହଞ୍ଚିବା ପାଇଁ ସେହି 3ଟିକୁ allowlist କରନ୍ତୁ, କିମ୍ବା ପରାମର୍ଶମୂଳକ ସ୍ତରକୁ ଅବନମିତ କରନ୍ତୁ। GitHub ର ନେଟିଭ୍ secret-scanning + `check:public-creds` ସହିତ ଏହା ଆଂଶିକ ଭାବେ ଓଭରଲାପ୍ କରେ।
- `check:pr-evidence` (ବ୍ଲକିଂ, PR-body ଗଦ୍ୟରେ grep କରେ) — ମିଥ୍ୟା-ପଜିଟିଭ୍ର ଉଚ୍ଚ ବିପଦ; ଏହାକୁ ବାଦ ଦେଲେ Hard Rule #18 ର ପ୍ରବର୍ତ୍ତନ ଦୁର୍ବଳ ହୁଏ, ତେଣୁ ଏହା ଏକ ପ୍ରକୃତ ନୀତିଗତ ନିଷ୍ପତ୍ତି।
- `semgrep` (ପରାମର୍ଶମୂଳକ ସ୍ୱତନ୍ତ୍ର) — OWASP ପରିବାରଗୁଡ଼ିକ ପାଇଁ CodeQL ସହିତ ଓଭରଲାପ୍ କରେ; ଏହାର ବେସଲାଇନ୍କୁ ଏକ ରାଚେଟ୍ ସହ ଯୋଡ଼ନ୍ତୁ କିମ୍ବା ବାଦ ଦିଅନ୍ତୁ।

#### `check-key-completeness` — କି-ସେଟ୍ ସମତା ଗେଟ୍

`scripts/i18n/check-key-completeness.mjs` (`npm run i18n:check-keys`, ଜବ୍ `i18n-ui-coverage`)।
କିଟି କେବେ ଯୋଡ଼ାଯାଇଥିଲା ତାହା ନିର୍ବିଶେଷରେ, ପ୍ରତ୍ୟେକ `src/i18n/messages/<locale>.json`-ର ଲିଫ୍ କି ସେଟ୍କୁ `en.json` ସହିତ ତୁଳନା କରେ ଏବଂ କୌଣସି ଅନୁପସ୍ଥିତ କିମ୍ବା ଅତିରିକ୍ତ ଲିଫ୍ ଥିଲେ ବିଫଳ ହୁଏ। `__MISSING__:` ପ୍ଲେସ୍ହୋଲ୍ଡର୍ଗୁଡ଼ିକୁ ଉପସ୍ଥିତ ବୋଲି ଗଣାଯାଏ (ସେଗୁଡ଼ିକର ବିଷୟବସ୍ତୁ ରେସିଓ ଗେଟ୍ର ଦାୟିତ୍ୱ)। ଏହା ଦୁଇଟି diff-ଆଧାରିତ/ପ୍ରତିଶତ ଗେଟ୍ର ପୂର୍ଣ୍ଣ ପରିପୂରକ: `check-ui-keys-coverage` ପ୍ରତ୍ୟେକ ଲୋକେଲ୍ ପାଇଁ 80 % ସର୍ବନିମ୍ନ ସୀମା ଲାଗୁ କରେ (~13,000 ମଧ୍ୟରୁ 43ଟି କି ଅନୁପସ୍ଥିତ ଥିଲେ ମଧ୍ୟ ଏହା 99.7 % ଦେଖାଏ) ଏବଂ `check-new-key-coverage` କେବଳ ଗୋଟିଏ PR ଦ୍ୱାରା `en.json`-ରେ ଯୋଡ଼ାଯାଇଥିବା କିଗୁଡ଼ିକୁ ବିଚାର କରେ। ଗୋଟିଏ ଲୋକେଲ୍ ବ୍ୟାଚ୍ର ବ୍ରାଞ୍ଚ୍ ତିଆରି ହୋଇଥିବା ଦିନର `en.json`-ରୁ ତାହା ଜେନେରେଟ୍ ହୁଏ ଏବଂ ବେସ୍ରେ ନୂଆ କି ଯୋଡ଼ାଯାଉଥିବା ବେଳେ ଏହା ଅନେକ ଦିନ ଧରି ଅନୁବାଦ କରେ; ବ୍ୟାଚ୍ PR ନିଜେ କୌଣସି କି ଯୋଡ଼େ ନାହିଁ, ତେଣୁ ବ୍ୟାଚ୍ 1 (#13044) ନଅଟି ଲୋକେଲ୍ରେ 43ଟି କି କମ୍ ଏବଂ ବ୍ୟାଚ୍ 2 (#13660) ଆଠଟି ଲୋକେଲ୍ରେ 10ଟି କି କମ୍ ଥାଇ ମର୍ଜ୍ ହୋଇଥିବା ବେଳେ ଉଭୟ ସହୋଦର ଗେଟ୍ ନିରବ ରହିଥିଲେ (2026-09-15)। ଏକ ବିଫଳତାକୁ
`node scripts/i18n/sync-ui-keys.mjs --locale=<codes> --translate-markers` ଦ୍ୱାରା ସମାଧାନ କରନ୍ତୁ; ଗୋଟିଏ `extra` ଲିଫ୍ର ଅର୍ଥ ହେଉଛି ଉତ୍ସରୁ ତାହା ବାଦ୍ ଦିଆଯାଇଛି — ଲୋକେଲ୍ରୁ ତାହାକୁ ଡିଲିଟ୍ କରନ୍ତୁ। `--warn` ବିଫଳ ନ କରି ରିପୋର୍ଟ କରେ।
`--catalog=cli`, `bin/cli/locales` ଉପରେ ସେହି ତୁଳନା ଚଳାଏ (`npm run i18n:check-keys:cli`);

#### `check-new-key-coverage` — ନୂଆ-କି i18n ଗେଟ୍

`check-ui-value-drift`-ର ସହୋଦର। ଇଂରାଜୀ ମୂଲ୍ୟଟି **ପୁନର୍ଲିଖିତ** ହୋଇଥିବା ବେଳେ ତାହାର ଅନୁବାଦଗୁଡ଼ିକ ଅପରିବର୍ତ୍ତିତ ରହିଗଲେ ପ୍ରଥମଟି ତାହା ଧରେ; କିନ୍ତୁ କୌଣସି ଇଂରାଜୀ କି **ଯୋଡ଼ାଯାଇଥିବା** ବେଳେ କିଛି ଲୋକେଲ୍ ତାହାକୁ କେବେ ପାଇ ନଥିଲେ ଏହା ସେହି ଘଟଣାକୁ ଧରେ।

`check-ui-keys-coverage` ଏହି ଶ୍ରେଣୀକୁ ଚିହ୍ନଟ କରିପାରେ ନାହିଁ: ଏହା ପ୍ରତ୍ୟେକ ଲୋକେଲ୍ ପାଇଁ ଗୋଟିଏ ପ୍ରତିଶତ ସର୍ବନିମ୍ନ ସୀମା ଲାଗୁ କରେ, ଏବଂ ~13,000ଟି ଲିଫ୍ରୁ ଏଗାରଟି କି ଅନୁପସ୍ଥିତ ଥିଲେ ମଧ୍ୟ କଭରେଜ୍ 99.9% ରହେ। ପ୍ରତ୍ୟେକ ଭାଷା ପାଇଁ ଗୋଟିଏ ପ୍ରତିଶତ ଦ୍ୱାରା "ଏହି ବୈଶିଷ୍ଟ୍ୟଟି ଅନୁବାଦ ବିନା ରିଲିଜ୍ ହେଲା" ବ୍ୟକ୍ତ କରାଯାଇପାରେ ନାହିଁ — କୌଣସି ଟେକ୍ସଟ୍ ବିନା ଗୋଟିଏ ସମ୍ପୂର୍ଣ୍ଣ ବୈଶିଷ୍ଟ୍ୟ ନୂଆ ଲୋକେଲ୍ରେ ଯୋଡ଼ାଯାଇପାରେ ଏବଂ ଏହି ସଂଖ୍ୟା କେବେ ବି ବଦଳିବ ନାହିଁ।

ଏହା ଯେଉଁ ଘଟଣାକୁ ସୂଚିତ କରେ: Orchestration Canvas-ର Phase 3 ସେତେବେଳେ ଥିବା 42ଟି ଲୋକେଲ୍ରେ ଏହାର ଏଗାରଟି କି ଅନୁବାଦ କରିଥିଲା। କିଛି ଘଣ୍ଟା ପରେ EU-ଭାଷା ବ୍ୟାଚ୍ (#13044) ରିପୋକୁ 51ଟି ଲୋକେଲ୍କୁ ନେଇଗଲା, ଏବଂ ନଅଟି ନବାଗତ ଲୋକେଲ୍ (`el`, `et`, `ga`, `hr`, `lt`, `lv`, `mt`, `sl`, `sr`) ସେଗୁଡ଼ିକୁ କେବେ ପାଇଲେ ନାହିଁ। `deepMergeFallback` ଏକ ଅନୁପସ୍ଥିତ କି ପାଇଁ ଇଂରାଜୀ ପ୍ରତିସ୍ଥାପନ କରେ, ତେଣୁ ବିଫଳତାର ରୂପ ଖାଲି UI ପରିବର୍ତ୍ତେ ଅନନୁବାଦିତ UI ଥିଲା — ଏକ ପ୍ରକୃତ ସମସ୍ୟା, ଯାହା ନିର୍ମାଣଗତ ଭାବେ ନିରବ ଥିଲା।
